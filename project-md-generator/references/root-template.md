# 根目录 md 文件模板

> 这是项目根目录 AI 记忆 md 文件（`CLAUDE.md` / `AGENTS.md`）的标准模板。生成时严格套用下方的章节顺序与标题，不要自创章节、不要调换顺序。

## 完整模板（复制后填充）

```markdown
# <项目名称>

> <一句话描述项目用途>

## 项目概述与技术栈



## 常用命令 (确保命令都可用)



## 包结构与分层



## 开发约束

- 严格遵守公司 skill 规范：CRUD 用 `crud-generator`、SQL 用 `sql-generator`、权限点用 `permission-generator`、字典用 `dict-generator`、接口同步用 `api-generator`、测试用 `test-generator`、代码审查用 `code-reviewer`。
- 日志要求：结构化日志，统一公式为 `log.级别("[线程id] [操作人] [业务模块] [业务动作], key1={}, key2={}", 值1, 值2[, 异常对象]);`。禁止自然语言长句、字符串拼接、打印完整大对象；必须使用 `{}` 占位符、包含唯一标识符（ID）、异常对象放最后一个参数，确保每条日志可被开发者 grep 追溯到来源。

## 注意事项



## 避坑指南



## 维护触发条件

以下内容发生变化时，必须同步更新本文件：

- 常用命令、构建方式、部署方式变化
- 项目结构变化
- 新增重要架构约束或业务约束
- Claude 多次犯同一种错误
- 发现新的安全风险或常见坑
- 某业务说明超过 10 行时，优先下沉到 docs 目录并在本文件保留链接

## 其他

```

## ⛔ 必须逐字一致的段落

以下两段是**公司全员统一口径**，在所有项目的根 md 里必须一字不差。生成时直接复制，禁止改写、删减或"优化"措辞——否则不同项目的约定会出现分叉，AI 反而无所适从。

### 1. `## 开发约束` 下的两条

```markdown
## 开发约束

- 严格遵守公司 skill 规范：CRUD 用 `crud-generator`、SQL 用 `sql-generator`、权限点用 `permission-generator`、字典用 `dict-generator`、接口同步用 `api-generator`、测试用 `test-generator`、代码审查用 `code-reviewer`。
- 日志要求：结构化日志，统一公式为 `log.级别("[线程id] [操作人] [业务模块] [业务动作], key1={}, key2={}", 值1, 值2[, 异常对象]);`。禁止自然语言长句、字符串拼接、打印完整大对象；必须使用 `{}` 占位符、包含唯一标识符（ID）、异常对象放最后一个参数，确保每条日志可被开发者 grep 追溯到来源。
```

> 这条 skill 规范列表与公司 lingman-skills 平台现有 skill 一一对应，确保 AI 在任何项目里都知道"该用哪个 skill"。日志公式与 `crud-generator` 的日志规范保持一致（四字段前缀 + 唯一 ID + 异常末位），详见 [../lingman-core/framework.md](../../lingman-core/framework.md)。

### 2. `## 维护触发条件` 整段

```markdown
## 维护触发条件

以下内容发生变化时，必须同步更新本文件：

- 常用命令、构建方式、部署方式变化
- 项目结构变化
- 新增重要架构约束或业务约束
- Claude 多次犯同一种错误
- 发现新的安全风险或常见坑
- 某业务说明超过 10 行时，优先下沉到 docs 目录并在本文件保留链接
```

> 这段把"什么时候必须回来改这个文件"写清楚，避免 md 文件慢慢和项目脱节、变成过时废纸。其中"某业务说明超过 10 行就下沉到 docs"是控制根 md 不超过 160 行的关键机制。

## 各填充段落写法指南

### `# <项目名称>` 与引言

- 标题用项目真实名称（从 `pom.xml` 的 `<name>` / `package.json` 的 `name` / 仓库名取）。
- 引言 `> <一句话描述项目用途>`：一句话讲清"这个项目是干嘛的"，不超过一行。

### `## 项目概述与技术栈`

简明列出：项目定位、核心技术栈（JDK 版本、Spring Boot 版本、数据库、前端框架等）、关键依赖。技术栈必须来自 `pom.xml` / `package.json`，不要凭印象。

### `## 常用命令 (确保命令都可用)`

只列高频命令：启动、构建、测试、lint、数据库迁移等。每条**核对来源**：

- 前端命令来自 `package.json` 的 `scripts`；
- 后端命令来自 Maven 目标 / `mvnw`；
- `lm` 系列 CLI 命令（如 `lm api`、`lm u`）确认项目已配置。

写法示例：

```markdown
## 常用命令 (确保命令都可用)

# 后端（在后端工程根目录）
./mvnw spring-boot:run          # 启动后端
./mvnw clean package            # 打包

# 前端（在前端工程根目录）
pnpm install
pnpm dev                        # 启动前端
pnpm build                      # 构建

# 接口同步（接口变动后）
lm api                          # 从后端 Swagger 生成前端接口定义
```

> 宁可少写几条但保证可用，也不要堆砌一堆跑不通的命令。"确保命令都可用"是硬要求。

### `## 包结构与分层`

用目录树展示关键分层，配简短说明。庞大项目的详细分层说明下沉到分层 md，这里只放顶层概览 + 指向分层 md 的链接。

### `## 注意事项` 与 `## 避坑指南`

- **注意事项**：开发时必须遵守的硬性约束（如"接口路径不可重复""非 GET 请求一律 `@RequestBody`"）。
- **避坑指南**：真实踩过的坑 + 解法（如"Flyway 脚本命名错了导致启动失败 → 检查 `V{n}__` 格式"）。

每条尽量带"为什么"，让 AI 理解而不是死记。这两节会随项目演进不断追加——每次 AI 犯错或发现新坑，就补一条进来（呼应"维护触发条件"里的"Claude 多次犯同一种错误"）。

### `## 其他`

兜底段落：环境变量、编码规范外链、贡献流程等不属于上面分类的内容。

## 行数控制

- 根 md **硬上限 160 行**。
- 任何一节内容超过约 10 行，就搬到 `docs/` 下的独立文件，在本节留一个链接。
- 优先用表格、短句、链接，而不是大段散文。
